# ADR-0007: Media Architecture: Self-Hosted LiveKit SFU (RG27) vs Mesh P2P vs Jitsi/Agora

## Status
Accepted (2026-10-25)

## Context
SmartClass requires interactive group video classes for 20 to 40 students per session with low latency, teacher audio/video, student audio/video, host-only screen sharing, and future recording/summarization capabilities (UC3, UC4, RG8, RG11, RG14). The solution must comply with French/European privacy and educational data sovereignty requirements (RG27: self-hostable, local infrastructure, no third-party vendor lock-in).

## Decision
Adopt self-hosted **LiveKit SFU** (Selective Forwarding Unit) deployed via Docker alongside the SmartClass backend and database:
1. **SFU Architecture**: Each participant sends their media stream once to the SFU server, which selectively forwards appropriate streams to other participants based on active speakers, layout, and client bandwidth.
2. **Simulcast & Quality**: Native support for WebRTC simulcast, dynacast, and adaptive streaming for varied client networks.
3. **Ecosystem & SDKs**: Official, actively maintained Flutter SDK (`livekit_client`) supporting Web, Android, iOS, and Desktop.
4. **Security & RBAC**: Token-based authentication using server-signed JWTs generated by the SmartClass Express API with fine-grained grants (room name, identity, metadata, publish permissions).
5. **Extensibility**: Native Egress service support for future server-side recording and AI summary pipelines.

## Alternatives Considered
- **Raw WebRTC Mesh (P2P)** — Rejected: In a full mesh, every participant uploads to $N-1$ peers, causing severe bandwidth and CPU exhaustion beyond 4–6 participants. Entirely unworkable for class sizes of 20–40 students.
- **Cloud CPaaS (Agora, Twilio, AWS Chime)** — Rejected: Violates RG27 data sovereignty, introduces recurring per-minute egress fees, and requires external internet egress for all internal educational media traffic.
- **Jitsi Meet** — Rejected: Heavier resource footprint, monolithic architecture, and complex custom integration compared to LiveKit's modular, headless SFU design with first-party Flutter client support.

## Consequences
- **Positive**: High scalability for classroom groups (20–40 users), minimal client upload bandwidth, strict compliance with RG27, robust official Flutter SDK, seamless integration with SmartClass user roles and permissions.
- **Negative**: Requires self-hosting the LiveKit server container, exposing appropriate UDP media ports (7882/udp) and TCP fallback (7881), and configuring ICE candidates for local development and production.

## Trade-offs
Self-hosting operational overhead is accepted in exchange for strict data sovereignty, absence of recurring per-minute SaaS fees, and native Flutter integration.
